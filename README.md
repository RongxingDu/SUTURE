# AWF

AWF is an experimental framework for API-based LLM agentic workflow
optimization. It separates workflow execution, query-level scheduling,
trace/reward collection, failure localization, constrained candidate edits,
counterfactual evaluation, and held-out experiment protocol.

## Install

```bash
python -m venv .venv
.venv/bin/pip install -e '.[dev]'
```

Set the API key expected by the configured OpenAI-compatible endpoint:

```bash
export OPENAI_API_KEY=...
```

Configuration inheritance is recursive. API keys are redacted from saved
experiment results.

## Run

See [experiments/README.md](experiments/README.md) for the complete command
tutorial: the one-click optimize-and-test pipeline script, the manual
`awf-optimize` / `awf-test` entrypoints, and the full configuration
parameter reference.

One-click pipeline (optimize then official held-out test):

```bash
bash experiments/scripts/run_optimize_and_test.sh \
  --config experiments/configs/math_aliyun_qwen35_full.yaml \
  --benchmark math \
  --data /path/to/benchmark.jsonl \
  --api-key "$ALIYUN_API_KEY"
```

Manual optimization:

```bash
awf-optimize \
  --config experiments/configs/math.yaml \
  --benchmark math \
  --data /path/to/gsm8k.jsonl
```

The optimizer creates reproducible optimization/validation/test splits,
validates the initial workflow as round 0, applies validation-based early
stopping, and writes a manifest binding the ordered dataset, exact split
indices, scientific config, and validation-selected checkpoint. It does
**not** evaluate the held-out test split.

After optimization, run the official test once with the exact same config,
ordered dataset, benchmark, and execution mode:

```bash
awf-test \
  --results experiments/results/math/results.json \
  --config experiments/configs/math.yaml \
  --benchmark math \
  --data /path/to/gsm8k.jsonl
```

`awf-test` rejects manifest mismatches and a second official evaluation, then
atomically records `test_metrics` and `test_evaluated_at` in `results.json`.

Code generated by an LLM is not executed by default. Production evaluation
must inject a `CodeRunner` backed by a real container or VM sandbox. The
`--allow-local-code-execution` option enables a resource-limited subprocess
runner only for trusted fixtures; it does **not** isolate the filesystem or
network. The code CLI otherwise refuses to start unless
`--allow-zero-hard-reward` explicitly acknowledges that hard reward will be
unavailable.

Counterfactual reruns likewise default to tools explicitly marked or
allowlisted as safe. Tools with side effects require a real sandbox or a
transaction adapter that can isolate and roll back their effects; do not
allowlist them as ordinary replay-safe tools.

Executor timeouts stop awaiting a timed-out step, but Python cannot forcibly
terminate a synchronous function already running in a worker thread.
Side-effecting production tools therefore need cooperative/async cancellation
or process/container isolation with their own timeout and rollback semantics.

## Objective

Hard reward utility and candidate gain are:

```text
R = R_hard + alpha * R_process
U = R_hard
G = delta_U - lambda_cost * (C_exec_candidate - C_exec_incumbent)
    - mu_edit * D_edit
```

`R` is retained as a process-quality diagnostic. `C_exec` is the recorded
input/output-token count; a reduction therefore contributes positively to
`G`. Latency, API cost, and runtime complexity remain separate diagnostics or
efficiency-anchor signals and do not alter `U`. In the legacy gain-driven
path, candidate edits are accepted only when:

```text
G > epsilon_stat
```

Failure-repair updates in the active inner path use the stricter suffix-replay
correctness gate described below; `G` is then only a tie-break after valid
repairs have been established.

The scheduler and optimizer both use API clients; no local model training or
inference is assumed.

## Correctness-grounded inner search

The active research path is deliberately inner-only. A round consumes
optimization-split failures, localizes an anchor, and proposes/evaluates
prompt, operator, or graph-path edits (the historical internal scope name for
graph path is `block`). The candidate gain is still
`delta_hard_reward - lambda_cost * delta_tokens - mu_edit * edit_distance`,
with the default edit coefficient reduced to `0.02`. For a failure-triggered
update, a candidate is promotion-eligible only if every triggered failure is
correct on suffix replay from the unchanged prefix; among eligible repairs,
the lightest edit is preferred and gain breaks ties. Selective gates,
high-cost-success triggers, and scheduler deviation remain disabled in this
mode. Fixed/graph schedulers remain only as deterministic execution
substrates.

The former inner-v2/outer-layer knobs are retained in the schema for historical
ablation reproducibility. They become active only in an explicit legacy run
with `workflow_content_only: false`:

```yaml
optimizer:
  workflow_content_only: false  # explicit legacy outer-layer ablation
  hard_success_threshold: 1.0
  min_success_guards: 1
  efficiency_optimization_enabled: true
  efficiency_anchor_fraction: 0.2
  efficiency_min_relative_cost: 1.25
  efficiency_max_anchors: 1
  candidate_archive_size: 3
  exploration_budget: 1
```

Selective Counterfactual Workflow Update (S-CWU), scheduler deviation, and
efficiency-triggered outer updates remain documented as future/legacy
ablations in
`experiments/results/deepseek_v4_flash/OUTER_LAYER_DESIGN.md`; they are not
used by the default experiments.

The explicit dual-layer cascade is configured separately with
`scheduler.scheduler_type: cascade`.  Its deterministic Gate follows the
template for low-confidence artifacts, early-exits high-confidence terminal
artifacts, and calls a compact DeepSeek-V4-Flash JSON scheduler only for the
borderline band.  `workflow_llm` can keep Qwen3.5-Flash as the base workflow
backend while `scheduler.llm` remains DeepSeek; see
`experiments/configs/math_aliyun_qwen35_dual_cascade.yaml`.

GPQA, MMLU, and SciCode pilot configs are also included. Install SciCode's
scientific evaluator dependencies with `pip install -e '.[scicode]'`; SciCode
requires the official `test_data.h5` plus the explicit bubblewrap execution
flag. GPQA/MMLU share the minimal one-call multiple-choice workflow. The
artifact-backed AFlow comparison adapter needs
`pip install -e '.[aflow]'`. The current local AFlow one-update integration is
GPQA-only; MMLU and SciCode support AWF/Vanilla evaluation but are not labelled
as implemented AFlow baselines.

The completed 12/4/4 GPQA mechanism pilot, including the negative held-out
efficiency result, is reported in
`experiments/results/deepseek_v4_flash/GPQA_S_CWU_PILOT_REPORT.md`. It should
not be interpreted as a statistically powered benchmark result.
The research-positioning matrix against AFlow, ADAS, ASpec, GPTSwarm, and OMAC
is in `experiments/results/deepseek_v4_flash/RESEARCH_POSITIONING.md`; only
Vanilla, AFlow, and S-CWU were executed in this pilot.
